Instructions for improving the Forensic Document Examiner app
Core Semantics (do not change the fundamental design)
The app does not decide whether a document is “real” or “fake” in absolute terms.
The user supplies a claimed identity (e.g. “This is an official UBS Financial Services account-freeze notice”).
The app’s job is to decide how well the document’s metadata, structure, and content support that specific claim.
“SUSPICIOUS” / low match means: “This document does not cleanly match the claimed identity.”
Required Improvements

Fix the false “No font metadata” finding
The current logic incorrectly reports “No font metadata despite extractable text.”
Real PDFs almost always contain font objects (even when text is extractable).
Change the detection:
Walk the page resources /Font dictionary (and any descendant fonts).
Count embedded fonts, subset fonts, and BaseFont names.
Only flag “no fonts” or “fonts stripped” when the page has extractable text and zero font objects are present.

When fonts exist, report them (or at least the count and whether they are subsetted).

Make every finding explicitly relative to the user’s claimed identity
Every finding should answer: “Does this fact support or undermine the specific claim the user made?”
Example language change:
Bad: “Named individual recorded as document author”
Better: “Author is an individual (‘Purdie, Terry’) rather than a UBS organizational identity. This weakens the claim that the document was generated by a UBS institutional system.”

Do the same for software origin, incremental saves, entity-name inconsistencies, etc.

Separate pure technical facts from interpretive judgments
Technical facts (Author, Creator, Producer, CreationDate, ModDate, number of %%EOF markers, linearized status, presence of AcroForm, font count, etc.) must be reported accurately and neutrally.
Interpretive findings (inconsistent entity names, unexpected author type relative to the claim, etc.) should be clearly labeled as interpretive and tied back to the claimed identity.
Never present an interpretive conclusion as a hard structural fact.

Improve incremental-update / multi-EOF detection
Keep detecting multiple %%EOF / startxref markers.
When more than one is present, report the exact count and note that the document was modified after initial creation.
Explicitly relate this to the claim only when the modification date or content raises a consistency issue with the claimed issuance circumstances.

Confidence score and verdict language
The confidence score should reflect how well the document matches the claimed identity, not an absolute authenticity score.
Preferred verdict labels:
STRONG MATCH
PARTIAL MATCH / NEEDS CORROBORATION
WEAK MATCH / INCONSISTENT WITH CLAIM
CLEARLY INCONSISTENT WITH CLAIM

Avoid absolute words like “forgery” or “authentic” unless the user specifically asks for an absolute judgment. Default language should stay relative to the claim.

Font and structure reporting (minimum viable improvement)
Always attempt to list or count fonts.
Report:
Number of font objects
Whether any are embedded / subsetted
Presence of AcroForm, JavaScript, embedded files, digital signatures, linearization, object streams, XRef streams

These should be shown in a clean “Technical Profile” section that is separate from the claim-relative findings.

Content inconsistency detection
Keep the ability to flag internal inconsistencies in the text (e.g., different legal entity names used for the same institution).
When such an inconsistency is found, explicitly state why it matters relative to the claimed identity.


Implementation Notes for the Agent

Prefer robust PDF parsing libraries that correctly expose font dictionaries, XMP, Info dictionary, and trailer structure.
Do not rely on heuristics that assume “text present = fonts must be missing.” That assumption is wrong.
Keep the existing UI structure (verdict card, findings list, extracted metadata panel, document history / software chain) but make the language and logic match the rules above.
All findings must remain explainable: the user should be able to see exactly which technical observation led to each judgment.

Apply these changes so the app becomes more accurate on structural facts while staying true to its core design: evaluating consistency with the user’s stated claim about what the document is supposed to be.
